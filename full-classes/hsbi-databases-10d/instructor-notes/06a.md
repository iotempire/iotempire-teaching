## What to expect

This is the session where the course's performance argument becomes visible. Students have heard "columnar is faster"; here they see **70–90×** on their own data and then see DuckDB lose **by 300×** on a workload it was not built for. Both halves matter. If the room only remembers "DuckDB is fast", the session failed.

Two things to say before anyone times anything:

- **Milliseconds, not 40 minutes.** The story is the plant's production dataset; the lab is 2M rows. The dashboard runs in ~7 ms, not 40 minutes.
- **The ratio and the plan travel; the numbers do not.** Their laptop will differ. That is fine.

## Before class

- [ ] Module 5 was one session and its homework (Rounds 5–7) is gated in the first 15 minutes here. Print or project the gate questions.
- [ ] `Module05/normalize.db` exists in your demo portfolio; if not, rebuild it with the Module 5 Setup block (~1 minute).
- [ ] Run `prepare.py` once. It writes a **112 MB** `history.db` and an 11 MB CSV. Check free disk.
- [ ] **Do not** use DuckDB's `INSTALL sqlite` / `sqlite_scanner`. It downloads into `~/.duckdb` and fails on locked-down machines and read-only homes. The module exports CSV on purpose.
- [ ] Know the bug you will hit: `CAST(r.done_on AS DATE) + (k * 91)` fails because `range()` yields `BIGINT`. The module uses `CAST(k * 91 AS INTEGER)`.

## Opening (15 minutes)

Run the **Module 5 gate** first. Two minutes per pod: storage numbers, rows touched by one site update, one memo read aloud. Do not re-teach normalisation. If a pod is missing it, "not yet", move on.

Then the story: *"The dashboard is fixed. Controlling now wants two years, and the report still runs on the operational database. Forty minutes, every month, at 02:00."* Ask the room what they would do — you will get "buy a bigger server", "build a data warehouse", "use Spark". Then: *"You have one laptop and a file. Go."*

## The rounds — what to check at each gate

| Round | What "good" looks like | Common wrong answer | Intervene when |
|---|---|---|---|
| **1 Build** | 2,000,000 rows; CSV ≈ 11 MB | 200,000 — they forgot the multiplier | the count is not 10× |
| **2 Convert** | Same row count **and** same `SUM(part_price)` on both sides | "the sizes match" | they never compared a checksum |
| **3 Race** | Three interleaved runs, medians, a ratio | one run each, "DuckDB is faster" | no table of numbers |
| **4 Plan** | Points at `Projections:` and the 2M row count | reads the SQLite plan only | no `EXPLAIN ANALYZE` output |
| **5 Boundary** | Inserts/lookups show the reversal; `executemany` tried | "DuckDB is slower, so it is bad" | they stop at the first number |
| **6 Decide** | Memo names what stays, what moves, and the refresh | "move everything to Parquet" | no staleness plan |

The verified reference numbers on a fast machine (median of 3):

```text
2,000,000 rows
dashboard: sqlite ~600 ms | duckdb ~8 ms   (~75x)
monthly  : sqlite ~540 ms | duckdb ~7 ms   (~76x)
size     : db 112.7 MB    | parquet 2.3 MB
inserts  : sqlite 0.8 ms  | duckdb ~290 ms (executemany ~108 ms)
lookups  : sqlite 0.8 ms  | duckdb ~100 ms
```

## Where it goes wrong

- **They compare different datasets.** Row counts alone are not enough — make them compare a sum. Most "DuckDB is only 3× faster" results are a missing quarter or a different date range.
- **`EXPLAIN ANALYZE` surprises them** because it *runs* the query. That is the point; it also means it is not free.
- **They time the first run.** Cold cache makes SQLite look terrible and the ratio dishonest. Interleave, three runs.
- **They think the Parquet is a database.** It is an artefact you rebuild; updates are a new file, not an `UPDATE`.
- **The 112 MB file in Git.** Say it before they commit: `*.db`, `*.csv`, `*.parquet` stay out.
- **"Can we just use DuckDB for everything?"** Send them to Round 5 and then to Module 6b's decision record.

## Harvest

**Collections, not explanations.** Nudge them toward: the `Projections:` line, the Parquet being **50× smaller** than the database, `range()` returning `BIGINT`, and the fact that 1,000 inserts cost a third of a second in an "analytics" engine. Swap at the break and at the end.
