## What to expect

This is the session where the course's performance argument becomes visible. Students have heard "columnar is faster"; here they see **roughly 100×** on the pure aggregate and then see DuckDB lose **by two orders of magnitude** on a workload it was not built for. Both halves matter. If the room only remembers "DuckDB is fast", the session failed.

Two things to say before anyone times anything:

- **Milliseconds, not 40 minutes.** The story is the plant's production dataset; the lab is 2M rows. The dashboard runs in ~7 ms, not 40 minutes.
- **The ratio and the plan travel; the numbers do not.** Their laptop will differ. That is fine.

## Opening (15 minutes): the Module 5 recap

**Before the recap, two minutes — only if the previous session was thin.** Name the empty room once, say that today's turnout is the signal for whether the course continues in person or moves to the online-pod/async route, close the topic, and start the recap. Do not ask for excuses or debate points in plenary; the cohort-specific wording belongs in the session's scratch sheet, not in the module. The recap is what the room came for.

**The architecture in one breath.** M1 local file → M2 schema/ER/contract → M3 query/plan/safety → M4 edge integrity → M5 normalize/denormalize → today the analytical copy. Say this before the Module 5 numbers; it turns the recap into one story rather than a list of tasks. Point at the same six-line timeline in the generated recap file, and do not retell the individual stories — the room was there.

**Not a gate and not a check — a walkthrough.** Generate the four things in the terminal (or open the saved recap file) and reveal them one at a time; talk for 10–12 minutes, spend the rest on hands and findings.

1. **What Module 5 built.** Flat table → 3NF decomposition → the deliberately denormalized `report_jobpart`. Say *why* the denormalization was a decision, not a mistake — that is the sentence students should carry into today.
2. **The three numbers everyone should have measured:**
   - storage: **≈4.07 MB normalized vs ≈11.09 MB denormalized** (≈2.7×);
   - one site update: **1 row vs 4,000**;
   - dropping `ix_report_machine` made the denormalized query **faster**, not slower.
3. **Findings and problems from the room.** B often did *not* beat A at 200k rows — mostly **cold cache**: the first query paid for the pages, the second inherited a warm buffer. The index scan hurt; `part` had only 10 rows; the five-row extract and the generator disagreed about `cnc-01`'s site. Ask: *"Who measured B slower than A?"* — that surprise is this module's lesson too: the engine and the plan decide, not the slogan. Today both sides get a warm-up run before timing.
4. **The bridge.** That report table is 200,000 rows and 90 days old. Lea Winter wants two years, and the report still runs on the operational database at 02:00.

**The read-time number (optional, one minute).** The warmed A/B check gives **A ≈ 26–28 ms** and **B ≈ 23 ms** — B is only ~15% faster at 200k rows, not 10×. Say it explicitly: denormalization buys a modest read gain at this size and pays 2.7× storage and 4,000 rows per site update. The win depends on size, plan and cache.

If a pod has no numbers, they take the generated recap numbers and note that they copied them. Do not re-teach normalisation; the recap is context, not content.

Then the story: *"The dashboard is fixed. Controlling now wants two years. Forty minutes, every month, at 02:00."* Ask the room what they would do — you will get "buy a bigger server", "build a data warehouse", "use Spark". Then: *"You have one laptop and a file. Go."*

## The rounds — what to listen for in each discussion

| Round | What "good" looks like | Common wrong answer | Intervene when |
|---|---|---|---|
| **1 Build** | 2,000,000 rows; CSV ≈ 11 MB | 200,000 — they forgot the multiplier | the count is not 10× |
| **2 Convert** | Same row count **and** same `SUM(part_price)` on both sides | "the sizes match" | they never compared a checksum |
| **3 Race** | Three interleaved runs, medians, a ratio | one run each, "DuckDB is faster" | no table of numbers |
| **4 Plan** | Points at `Projections:` and the 2M row count | reads the SQLite plan only | no `EXPLAIN ANALYZE` output |
| **5 Boundary** | Inserts/lookups show the reversal; `executemany` tried | "DuckDB is slower, so it is bad" | they stop at the first number |
| **6 Decide** | Memo names what stays, what moves, and the refresh | "move everything to Parquet" | no staleness plan |

The verified reference numbers on a fast machine (median of 3–5):

```text
2,000,000 rows
dashboard: sqlite ~600 ms | duckdb ~6 ms   (~100x)
monthly  : sqlite ~540 ms | duckdb ~9–18 ms (~30–60x; strftime runs per row)
monthly + date_trunc:          duckdb ~9 ms  (~60x; same result)
size     : db 112.7 MB    | parquet 2.3 MB
inserts  : sqlite 0.8 ms  | duckdb ~290 ms (executemany ~108 ms)
lookups  : sqlite 0.8 ms  | duckdb ~100 ms
```

The discussions are **two minutes, pod to pod, no instructor**. Walk and listen. If a discussion stays at "it is faster", ask one of the questions in the module's discussion block — do not answer it. The point is that the pair says the reason out loud; that is where the learning goal is met or not.

## Where it goes wrong

- **They compare different datasets.** Row counts alone are not enough — make them compare a sum. Most "DuckDB is only 3× faster" results are a missing quarter or a different date range.
- **`EXPLAIN ANALYZE` surprises them** because it *runs* the query. That is the point; it also means it is not free.
- **They time the first run.** Cold cache makes SQLite look terrible and the ratio dishonest. Interleave, three runs.
- **They confuse the warm-up demo with the A/B race.** Section 6 runs the *same* query on `report_jobpart` twice; it isolates the cache. The normalized-vs-denormalized comparison was Module 5. Dropping caches before the whole demo does not make section 6 cold — sections 3–5 already touch the file. Drop caches *after* them and run only the two section-6 queries for a real cold first run. On NVMe the difference may still be small; 11 MB is fast.
- **They think the Parquet is a database.** It is an artefact you rebuild; updates are a new file, not an `UPDATE`.
- **The 112 MB file in Git.** Say it before they commit: `*.db`, `*.csv`, `*.parquet` stay out.
- **"Can we just use DuckDB for everything?"** Send them to Round 5 and then to Module 6b's decision record.
