## What to expect

The session where "relational is the only option" finally breaks. Students are usually surprised by two things: how far JSON-in-SQLite goes, and how *fast* a columnar engine is on the same file.

Two environmental risks, both real:

1. **DuckDB's SQLite extension is downloaded on first use** (`INSTALL sqlite`). On a locked-down network this fails. Have a fallback: export to CSV/Parquet from Python's `sqlite3` instead, and compare DuckDB-reading-Parquet against SQLite-reading-the-table. The point survives; the extension does not matter.
2. **`uv run` may need to resolve `duckdb` on first run.** Pre-warm the environment before class, or the first student to run it stares at a download.

## Opening (5 minutes)

Cirrus's line from Module 1: the cloud stack nobody needed. Then push it one step further — *"if you would not host a server for 5,000 rows, why would you force every workload into one storage model?"* The palette table is the answer, and the card sort is how they internalise it.

## Running the studio

- **Task A (card sort, 15 min).** The productive conflict is cards 1 and 2: an append-heavy ingest and a two-year weekly aggregation. If every pod picks SQLite for both, ask what happens at 50 million rows. They should land on "two engines, or one plus an export".
- **Task 1 (JSON).** The expression index is the real content: `CREATE INDEX … ON device(json_extract(meta,'$.vendor'))` works only if the `WHERE` uses the *identical* expression. Have them prove it with `EXPLAIN QUERY PLAN`, then break it by writing `meta ->> 'vendor'` in the query.
- **Task 2 (DuckDB).** Show the Parquet file size next to the SQLite file size — the comparison is more convincing than the timing.
- **Task 3 (key-value).** The numbers are stark (tens of seconds for `shelve` writes versus a fraction of a second for SQLite); ask what `shelve` is bad at, then ask what SQLite can do that a dict cannot.
- **Task 4 (name the paradigm).** This is the checkpoint question in miniature. Make every pod say its answer out loud before they leave.

## Where it goes wrong

- **"NoSQL means no schema."** The JSON column has a `CHECK (json_valid(meta))` and an index on the paths they query — it *is* a schema, just a flexible one. Say it.
- **DuckDB treated as a server.** It is a library. If a student starts a daemon, the mental model has not landed.
- **Parquet edited by hand.** It is an output format for this course; the editable copy stays in SQLite.
- **Timing two different workloads.** Comparing a `SELECT *` on SQLite with an aggregate on Parquet proves nothing. Same query, two engines, or it is not a comparison.

## Read up on

- [DuckDB: why DuckDB](https://duckdb.org/why_duckdb) — row vs columnar in one page.
- [SQLite JSON1](https://sqlite.org/json1.html) — `json_extract`, `->`, `->>`, `json_each`.
- Parquet's columnar layout, enough to explain why a scan reads less.
- ACID vs BASE, and why CAP does not apply to a single-file database — you will be asked.
