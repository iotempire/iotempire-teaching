## What to expect

This session starts with the shared server, not with JSON. That is deliberate:

- The server is the riskiest logistics. If it fails, you want it at minute 5 with the whole session ahead of you — not at minute 120.
- The whole room on one server, then the instructor stops it, is the strongest “why remote is different” moment in the course.
- The TA is most useful at the start, handling logins, while you run the stop/restart.
- JSON is quieter individual work after the break. The room has settled by then.
- It protects the server lesson from being cut. JSON can bleed into homework; the shared server cannot.

The session is **two content tasks and one decision**, not four content tasks. The decision record is the spine: Task 1 fills the optional “concurrent users” row, Task 2 fills the metadata and session-state rows, and the report/ingest rows come from 6a and Modules 1/4. Students always know where they are.

There is **no homework in the middle**. The key-value benchmark, the project ticket, the reflection, and finishing the record are all at the end. Weak linear students should never have to jump to a homework task and come back.

The TA gives feedback and may suggest readiness or a recheck; the TA does **not** record points or grades.

## If you are shaky on ACID, BASE, and CAP

You do not need the theory to run the task, but students will ask. Keep three pictures:

- **ACID — one database, one transaction.** *Atomicity*: all or nothing. *Consistency*: constraints
  hold before and after. *Isolation*: concurrent transactions do not see each other’s half-work.
  *Durability*: after commit, a crash does not lose it. Picture a bank transfer: the money leaves
  one account and arrives in the other, or neither happens.
- **BASE — a distributed system choosing availability.** *Basically available*, *soft state*,
  *eventually consistent*. Picture a social feed: a like may show late, then catch up. It is a
  deliberate trade, not a broken database.
- **CAP — the choice when the network splits.** A distributed system can keep *consistency* or
  *availability* when a partition happens, not both. Since partitions happen, real systems choose
  **CP** (refuse/stall rather than answer wrong) or **AP** (answer, possibly stale). An embedded
  SQLite file does not distribute, so CAP is not the choice it faces; it gives you ACID on one
  machine.

**One sentence to remember:** *ACID is a bank transfer, BASE is a social feed, CAP is the choice
when the network breaks — and SQLite is ACID on one machine because it does not distribute.*

Do not teach CAP as “pick two of three.” Partitions are not optional; the choice is C or A during
the partition. The full text and the module appendix are in
[Appendix A](../modules/06b-polyglot-persistence.md#a-acid-base-cap).

## If a student asks about XML databases

The native XML database wave (MarkLogic, BaseX, eXist-db, Sedna) is the direct ancestor of today’s
document stores and JSON columns. It made the same promise: store documents as they arrive, let the
schema evolve, query the structure with XPath/XQuery. It was real for document-centric publishing,
archives, and catalogues; the overreach was treating XML as the universal data model for every web
API and enterprise integration, which produced SOAP/WS-* and what critics called the “angle bracket
tax.”

**The anecdote to tell (your own experience; adapt the wording).** In the early 2000s, startups and
business-software teams pitched “XML databases” as the end of the fixed schema: the document
arrives, the database indexes it, no migration. The pitch was partly right — the document model was
real — but the universal-XML middleware around it (SOAP, WS-*, XSD) burned a lot of money for a lot
of teams. JSON and YAML then won the web and config layers by being smaller and mapping to the
language people already used.

The balanced take: the *document/semi-structured idea* was right and survived; the *universal-XML
middleware* was a costly hype cycle. Do not let the room turn it into a pure “XML was a scam” rant;
use it to make the schema point: **the format is not the schema**. XSD, JSON Schema, `json_valid`,
and an expression index are ways to make the implicit schema explicit. Point interested students at
the [reading list](../modules/Z-resources-bank.md#xml-databases-and-the-schema-debate) and
[Appendix B](../modules/06b-polyglot-persistence.md#b-schemaless-is-not-schema-free).

## Task 1 — the boundary (35 min)

### Setup for this run

**Primary.** The Optiplex (8 GB) runs Debian Trixie with native PostgreSQL 17 and pgweb; a
Cloudflare named tunnel exposes **pgweb only** at `hsbi-dbs.ulno.net`. Postgres stays on
`127.0.0.1` and is never published. One database and one role per pod from the actual pod list;
run the setup script with the real count, not a hard-coded 20. Passwords go on the LMS and on the
TA’s printed sheet.

**The connection host.** On the native setup, pgweb connects to PostgreSQL at `127.0.0.1:5432`;
on the container fallback it is `db:5432`. Put the correct host on the sheet. Students log into
pgweb with the shared class credentials, then use that host, port, database/user `podNN`, and the
pod password.

**Certificate and credential handout.** Cloudflare provides the public TLS certificate; students
need **no client certificate**. Hand out only the HTTPS URL, the pgweb basic-auth login, and the
per-pod database credentials. Never hand out `cert.pem` or the tunnel credentials JSON — those
allow managing the tunnel. The full setup, including the credential sheet template, is in the
[server setup guide](./postgres-server-setup.md).

**Plan B.** The container fallback is [`postgres-tunnel.sh`](./postgres-tunnel.sh): `up
hsbi-dbs.ulno.net`, or `up --quick` for a temporary URL, or `up --lan` for the classroom LAN. The
lesson is identical; only the connection host (`db`) and the credential handout are different.

- pgweb is the only exposed service; Postgres binds to localhost or the LAN, never a published
  5432. Cloudflare provides TLS; keep basic auth on pgweb.
- One database and one role per pod; no superuser, no `CREATEDB`, no cross-pod access.
- Test from a student laptop on the **campus Wi-Fi**, not only from the instructor machine.
- **Pre-create the `machine` table and one row in every pod database** before class.

### The table (pre-create it in every pod database)

```sql
CREATE TABLE machine(
    machine_id      INTEGER PRIMARY KEY,
    site            TEXT NOT NULL,
    parts_produced  INTEGER NOT NULL DEFAULT 0
);
INSERT INTO machine VALUES (1, 'guetersloh', 0);
```

This is deliberately not Module 4’s `sensor` table. Module 4 has `sensor`/`reading`; the legacy
`machine` table is Module 2. Module 4’s DDL also uses SQLite-only `STRICT`/`PRAGMA`, and its
`reading` table uses a `VIRTUAL` generated column that PostgreSQL does not support. The DML is
portable; the DDL is not.

### Run the moment

1. **Connect (0–5 min).** Pods log into pgweb with the shared class credentials, then use the host
   from the sheet, port `5432`, database/user `podNN`, the pod password, and **SSL mode `disable`**
   (pgweb-to-Postgres is local; Cloudflare TLS is browser-to-pgweb). The TA circulates; the
   instructor watches the room, not the screen.
2. **Inspect and query (5–7 min).** Students read the pre-created table, run a `SELECT`, and insert
   one row with an explicit `machine_id`. They do not run `CREATE TABLE` again. Point out the two
   dialect differences: no `STRICT`, no `PRAGMA`; the DML is the same.
3. **Concurrent write (7–22 min).** Use two different browsers or two student devices; two tabs in
   one browser may share a pgweb session. Both run
   `UPDATE machine SET parts_produced = parts_produced + 1 WHERE machine_id = 1;` — one waits,
   then succeeds. Then project the `psql` version in two terminals:
   - Session A: `BEGIN; UPDATE machine SET parts_produced = parts_produced + 1 WHERE machine_id = 1;`
     and hold.
   - Session B: the same `UPDATE` — it blocks.
   - Session A: `COMMIT;` — Session B proceeds.
   - Finish with the lost update: both sessions read the same value, then both write that value + 1,
     so one increment disappears. The server serializes writes; it does not fix application logic.
4. **Lose the server (22–27 min).** Stop only the database. On the native server:
   `sudo systemctl stop postgresql`; restart with `sudo systemctl start postgresql`. On the
   container fallback: `docker compose -p dbs-pg-bench stop db` / `start db` (or `podman compose`).
   Keep pgweb and the tunnel up. Every client fails; after the restart, reload pgweb and run the
   query again. Do not use `postgres-tunnel.sh down` in class — it also tears down the tunnel.
5. **Write three observations (27–32 min).** Easier, harder, one failure mode an embedded database
   does not have.
6. **Debrief (32–35 min).** Use the ACID/BASE/CAP mnemonic; ask which guarantee changed when the
   server stopped. Keep it to three minutes. The full text is in Appendix A; do not turn it into a
   lecture.

### Fallback if the server is unavailable

Run the SQLite two-writer comparison on the projector:

```python
import sqlite3

a = sqlite3.connect("two.db", timeout=1)
b = sqlite3.connect("two.db", timeout=1)
a.execute("CREATE TABLE IF NOT EXISTS t(id INTEGER PRIMARY KEY, v INTEGER)")
a.execute("INSERT OR IGNORE INTO t VALUES (1, 0)")
a.commit()
a.execute("BEGIN IMMEDIATE")
a.execute("UPDATE t SET v = v + 1 WHERE id = 1")
try:
    b.execute("BEGIN IMMEDIATE")
    b.execute("UPDATE t SET v = v + 1 WHERE id = 1")
    b.commit()
except sqlite3.OperationalError as e:
    print("second writer:", e)
a.rollback()
```

The second writer gets `database is locked`. That is the local version of the concurrency lesson;
the three observations still apply.

## Task 2 — the shape (40 min)

### Say this before the script

“This is not a JSON syntax lesson. It is the metadata row of the decision record. Three options: a wide table plus a migration per vendor field; a separate document database that loses the join to `machine`; or a JSON column in SQLite with `json_valid` and an expression index. The middle path has a price: the index only matches the exact expression, and `->>` is a different expression.”

### JSON (20 min)

- The script creates `device` with **1,000 rows**. The 3-row version still picked the expression
  index on SQLite 3.54, but that is a planner accident; the larger table makes the lesson stable.
- Output is trimmed to five rows. Students should compare the two `EXPLAIN QUERY PLAN` lines, not
  read 1,000 rows.
- Expected: `json_extract(meta, '$.vendor')` → `SEARCH device USING INDEX ix_device_vendor`;
  `meta ->> 'vendor'` → `SCAN device`.
- The Module 4 callback is deliberate: `CHECK (json_valid(meta))` is the constraint idea returning.
  Say it once; do not re-lecture Module 4.
- Common wrong answer: “the index does not work.” The index works for the expression it was built
  on; `->>` is a different expression.
- If the room is slow, keep the plan pair and move the second explanation to homework. Never move
  the plan pair itself; it is the evidence for the metadata row.

### Key-value briefing (5 min, homework)

- Do **not** run the 20k loop in class. Brief it; the code is in the module’s *After the studio*
  section.
- Reference numbers from the verified 20k run: `shelve` set ≈ **4.0 s**, SQLite set ≈ **0.02 s**;
  reads both ≈ **0.05–0.06 s**. Windows may be much slower for `shelve`; ask for orders of
  magnitude, not decimals.
- The lesson: reads tie, writes lose, and the argument for the key-value store is **simplicity**,
  not lookup speed.
- Today’s decision record uses the reference numbers and writes `reference` in the session-state
  `Evidence` cell. The homework replaces it with the pod’s own numbers and notes what changed.

### Contrast discussion (5 min)

- Document vs. key-value vs. relational: what did each buy, and what did it cost?
- “Are Anke’s metadata and Yasmin’s session state the same problem?” No: one is a document with
  queryable paths, the other is a pure key lookup. Same “not a table” label, different shape.
- The XML history is in Appendix B; do not lecture it. Use the anecdote only if a student asks.

## Task 3 — the decision (55 min)

- Four rows: ingest, report, vendor metadata, session state; optional fifth for concurrent network
  users. The first row in the module is a filled example; use it to calibrate depth.
- The report row comes from 6a; the ingest row uses the Module 4 idempotent `UPSERT`, the
  double-run row count, and the Module 4 constraint as evidence. Students do not need a new
  benchmark for ingest; the "crash must not lose rows" claim is an observation about SQLite's
  transactional commit and single writer, not a new crash test.
- The metadata row uses the JSON plan pair; the session-state row uses the reference numbers until
  the homework replaces them.
- Peer defence: **10 minutes each way + 5 minutes to write what changed**. If the room is fast, use
  12 each way. All pairs defend simultaneously; the instructor walks and listens. Ask one pair to
  read a changed row aloud at the end.
- The exit ticket is the “only one engine” line. If a pod cannot answer it, the record is not done.
- The record can be finished at home; the defence is in class.

## Where it goes wrong

- **Server first without a pre-test.** Test from a student laptop on the campus Wi-Fi before the
  session. If it is not ready, run the SQLite fallback, then JSON, then the decision.
- **Two tasks hide a stuck pod.** Use two sub-checkpoints: after Task 1, show the three
  observations; after Task 2, show the two JSON plans (and later the KV numbers).
- **“NoSQL means no schema.”** The JSON column has `json_valid` and an expression index on the paths
  they query — it *is* a schema. Say it.
- **The expression index that is not used.** `json_extract(meta,'$.vendor')` and
  `meta ->> 'vendor'` are different expressions. The second gets a `SCAN`. That is the task.
- **`STRICT` fails in PostgreSQL.** Module 4’s DDL is SQLite-only. The pre-created table is
  deliberately minimal; do not let students paste `STRICT` or `PRAGMA` into pgweb.
- **`shelve` numbers on Windows** look nothing like on Linux. Ask for the order of magnitude.
- **Expect writes to lose badly and reads to tie.** The argument for a key-value store is
  simplicity, not lookup speed — make them say that.
- **The CAP debrief becomes a lecture.** Three minutes, one question: which guarantee changed? The
  appendix is for the students who want more.
- **The record becomes an essay.** One page, one row per workload, evidence in the cells. If it is
  longer, it will not be defended.
- **The record stays on `reference` for the session state.** That is a recheck item, not a reason to
  re-teach the benchmark in class.
