## What to expect

This is the session where the course's thesis gets tested against reality. Students have spent six sessions hearing that an embedded database is enough; now they see a real server, watch it fail, and have to decide where the boundary is. **The goal is not to make them prefer SQLite — it is to make the choice explicit and evidenced.**

The decision record is the only artefact that matters. Everything else feeds a row into it. If the room runs out of time, cut a bench, not the defence — defending a choice is the skill the project will ask for.

## Before class

- [ ] **Module 4 callback.** The JSON bench uses `CHECK (json_valid(meta))` — the constraint idea from Module 4. Module 4 was a rough session for this cohort; say out loud that this is the same skill returning with a friendlier example, and that the project needs one constraint plus one trigger. Do not re-lecture it.
- [ ] Run `json_bench.py` on a clean machine. It needs SQLite ≥ 3.37 for `STRICT` (Python 3.14 ships a newer one).
- [ ] Run `kv_compare.py`. `shelve` is platform-dependent; on Windows it can be much slower. Report orders of magnitude.
- [ ] If you run the server bench: containers up, one database and role per pod, pgweb reachable, URLs on the board. Test from a student device, not from the server. The quickest path is [`postgres-tunnel.sh`](./postgres-tunnel.sh): `up --quick --dry-run` to see the plan, then `up --quick` (or `up db.example.com` for a stable hostname). `status` and `down` are the rest.

## Opening (10 minutes)

Recap 6a in one sentence: *"The report moved to a file and got roughly 75× faster."* Then the three shapes: a JSON column for metadata that keeps changing, a key for session state, a file for analytics. Ask: *"Do we need three engines — or is this one database with a bad schema?"* Do not answer. The decision record is the answer.

## The benches — what to listen for in each discussion

| Bench | What "good" looks like | Common wrong answer | Intervene when |
|---|---|---|---|
| **1 JSON** | `SEARCH … USING INDEX` for `json_extract`, `SCAN` for `->>` | "the index does not work" | they never compared the two expressions |
| **2 Key-value** | Four numbers and a reason; names the cross-session query | "`shelve` is faster, so use it" | no cost named |
| **3 Server** | Three concrete observations | "the server is better/worse" | no failure mode named |
| **4 Record** | Every row has evidence; the last line is defensible | "it depends" | a row with no measurement |

## Server bench — the options, and what each costs you

> **Draft, first-run notes.** These are alternatives, not a recommendation you must follow. Pick **one** — running two is how the session disappears into infrastructure.

First, the distinction that decides everything: **in class, on your own access points, students are on the LAN.** No public proxy is needed for the bench. A tunnel only matters if the server must be reachable **outside the room** — at home, in the project weeks, or from a different network.

| Option | Setup | Per session | Per term | Exposure | Survives the term? | Best for |
|---|---|---|---|---|---|---|
| **A** Instructor laptop + Podman + tunnel | 1–2 h | ~10 min | ~1 h | public via tunnel | no | one bench |
| **B** Fixed server (Optiplex) + tunnel | 2–4 h | ~10 min | 2–3 h | public via tunnel | yes | the whole class + project weeks |
| **C** Nebula overlay for the class | 4–8 h + a session | ~20 min | 3–4 h | none (private overlay) | yes | courses already running Nebula |
| **D** Student-local containers | 0 for you | ~20 min support | 0 | none | per student | capable students |
| **E** Managed Postgres (Neon/Supabase) | ~1 h | 0 | account admin | vendor | yes | no hardware, no ops |

Estimates are rough, from one run. The **per-term** effort is the column people underestimate.

### A — Instructor laptop + Podman + a tunnel

**Pros:** nothing to buy, one machine to manage, fast to reset; Podman on CachyOS is rootless and daemonless; the same compose file works with Docker Desktop on macOS/Windows.

**Cons:** the laptop must stay awake and online for the whole slot; the URL changes unless you own a domain and run a named tunnel; no persistence after class; the AP is still the bottleneck.

**Tunnel choices:**

- **Cloudflare quick tunnel** — `cloudflared tunnel --url http://localhost:8081` gives a random `trycloudflare.com` URL in seconds, no account. Fine for one session, useless for the term.
- **Cloudflare named tunnel** — stable hostname, needs a domain on Cloudflare. ~20 min setup.
- **Tailscale** — `tailscale serve` exposes to your tailnet only (students need Tailscale); `tailscale funnel` exposes publicly over HTTPS. Stable names, easy auth story.
- **Caddy + a public IP** — only if the campus actually gives you inbound 80/443; usually it does not.

**Consequence:** a tunnel is a public HTTPS endpoint into a database UI. Treat it as such (security baseline below), and expect to tear it down after the session.

> **Ready-made:** [`postgres-tunnel.sh`](./postgres-tunnel.sh) does A end to end. `up db.example.com` runs the one-time browser login, creates a named tunnel, routes the DNS record, starts Postgres 17 + pgweb in containers, and prints per-pod credentials. `up --quick` gives a random `trycloudflare.com` URL for instructors without a domain; `--lan` also publishes pgweb on the classroom LAN; `status` and `down` are the rest. `--dry-run` prints everything without starting it.

### B — Fixed server (Optiplex) on the LAN + a tunnel

**Pros:** stable hostname for the term; students can keep using it in the project weeks; the TA can restart it; one place for backups; you can run pgweb *and* a Datasette for their projects on the same box. This is the only option that turns the bench into a **service**.

**Cons:** a machine to patch, power, cool and physically secure; one disk or power supply is a single point of failure; the campus uplink is another; and someone has to decide what happens in February.

**Maintenance, realistically:**

- ~2–4 h initial setup (OS, containers, tunnel, per-pod roles, board with URLs).
- ~10 min before each session (containers up, disk not full, tunnel up).
- ~15 min/week during the term (updates, log check, disk).
- ~1–2 h/term for patching and the tunnel/domain.
- Incident time when it dies — budget for one afternoon.

**If it should survive the term, decide two things on day one:**

1. **Sandbox or service?** A sandbox can be reset weekly (`DROP DATABASE` + recreate) and needs no backups. A service needs nightly `pg_dump` and a restore test. Say which one it is, in writing, or students will store their project in it.
2. **Pods or teams?** In session 8 two pods merge into a Project Team. Either give each **team** one database from the start (and tell the pods to share), or keep pod databases and let a team use two. Do not migrate mid-project.

**Reset script sketch:** create roles/databases from a list, `pg_dump` per database, and a `reset.sh` that drops and recreates. The reset is the feature: it makes the box safe to break.

### C — Nebula overlay for the whole class

**Pros:** no public surface at all; the database is reachable only from enrolled hosts; it is the course's own technology, so it teaches something real; works from home and from the lab.

**Cons:** this is the most expensive option in **student time**, not instructor time. Every student installs a client, receives a certificate, imports it, accepts a firewall prompt, and debugs why it does not connect — on Windows, macOS, Linux. Certificates are credentials: they must not land in the public repo or a shared drive.

**What it actually costs:** a lighthouse with a public IP, a CA, per-student configs, a distribution channel that is not the course repo, and a helpdesk. Plan a **full 90-minute session** (or a TA clinic) before the database bench — and expect a third of the room to still need help. Do not attempt it for a 25-minute contrast; do it if the course **already** runs on Nebula and the client is installed in week 1.

**Nice side effect:** once the overlay exists, the Optiplex can serve the project teams for the rest of the term without exposing anything.

### D — Student-local containers (allow, do not require)

**Pros:** no server for you to run, no network dependency, and the failure demo is personal — *“stop your own container”* is more memorable than watching someone else's. Works offline after the image is pulled.

**Cons:** on Windows this means Docker Desktop or Podman Desktop, which need WSL2, virtualization enabled in the BIOS, and admin rights — three things a managed university laptop may not allow. Image pulls need network on first run. You will debug 20 different environments.

**Policy that works:** offer a compose file, say *“if you already run Docker or Podman, you may do the bench locally”*, and keep the hosted instance as the default and the fallback. Never make the local install a requirement for the lesson.

### E — Managed Postgres (one line, for completeness)

Neon or Supabase give you a browser SQL editor and per-project roles with zero ops. Great if you have no hardware and no appetite; the trade is a vendor account, a network dependency, and student data leaving the room. For fake plant data that is acceptable; say so explicitly.

## The setup we ran: one cluster + pgweb

**Yes, an old Optiplex will do it.** One PostgreSQL cluster with **20 databases and 20 roles** (not 30 containers) plus one pgweb is a rounding error for the hardware:

| Resource | Minimum | Comfortable |
|---|---|---|
| CPU | 2 cores (any 4th-gen i5/i7) | 4 cores |
| RAM | 2 GB | 4 GB — 8 GB is more than enough |
| Disk | 10 GB free | SSD, not HDD — the demo should feel responsive |
| Network | wired uplink to the AP | gigabit; the AP is the bottleneck, not the server |

The memory math: `shared_buffers` 256 MB, plus ~5–10 MB per connection. Twenty pods browsing pgweb is well under 1 GB of database process memory. Raise `max_connections` to 200 and keep `work_mem` modest.

**Docker / Podman:** Docker Engine on Linux is the easy path; Docker Desktop on Windows at 4 GB is tight. On the Optiplex, install a plain Linux and run Compose. On CachyOS, **Podman** runs the same file rootless: `podman compose up -d` (or `podman kube play` for a Kubernetes YAML). The compose file below is the whole setup either way.

```yaml
# docker-compose.yml — one cluster, one web UI, nothing exposed directly
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: change-this
    command: ["postgres", "-c", "max_connections=200", "-c", "shared_buffers=256MB"]
    volumes: ["pgdata:/var/lib/postgresql/data"]
    ports: ["127.0.0.1:5432:5432"]      # localhost only — never publish 5432
  web:
    image: sosedoff/pgweb
    environment:
      PGWEB_AUTH_USER: class
      PGWEB_AUTH_PASS: change-this-too
    ports: ["8081:8081"]
volumes:
  pgdata:
```

Then create one role and one database per pod (loop `pod01` … `pod20`, or generate the SQL):

```sql
CREATE ROLE pod03 LOGIN PASSWORD 'pod03-secret';
CREATE DATABASE pod03 OWNER pod03;
```

Students open **pgweb** (the only exposed service), type their database, user and password, and get a browser SQL console. **No client install, no `psql` on Windows, no admin rights.** Postgres itself stays on localhost or the LAN.

**The lesson lands in the last two minutes.** Have everyone write a row, then stop the database container. Every client fails at once, and no SQL fixes it. Restart it. Ask what an embedded database would have done. Then move straight to the decision record.

**Tunnel:** if you expose it beyond the room, expose **only pgweb**, never 5432 — the options and their trade-offs are in section A above.

### Security baseline (for any option that touches a network)

- Postgres binds to `127.0.0.1` (or the overlay IP). Never `0.0.0.0`, never a published 5432.
- Only the **web UI** is exposed, behind basic auth and TLS (the tunnel provides TLS).
- One role per pod, owning one database; no superuser, no `CREATEDB`, no access to another pod's database.
- Passwords per pod, on the board or in the LMS, rotated or discarded at term end.
- **Fake data only.** No student names, no real exports, no personal data — this is also the GDPR-sane choice.
- Proxy logs on; rate limit if the tunnel supports it.
- Have a teardown step: stop containers, revoke the tunnel, delete the volumes — or reset the databases.

### If it fails in the room

1. **Postgres up, pgweb down** — restart the `web` container, check the port.
2. **Pgweb up, tunnel down** — fall back to the LAN URL written on the board.
3. **Both down** — ten-minute instructor demo, then straight to the decision record.
4. **AP down** — demo on the machine itself, projected.

Never debug infrastructure for more than ten minutes in front of the room. The lesson survives without the server; the schedule does not.

### Term end

Decide in advance: reset and keep, or shut down and archive. If teams used it, `pg_dump` per team first. Announce the date early — *“the server disappears in February”* is a sentence students should hear in January.

## Where it goes wrong

- **"NoSQL means no schema."** The JSON column has `json_valid` and an index on the paths they query — it *is* a schema. Say it.
- **The expression index that is not used.** `json_extract(meta,'$.vendor')` and `meta ->> 'vendor'` are different expressions. The second gets a `SCAN`. That is the bench.
- **`STRICT` fails on an old SQLite.** Check `sqlite3.sqlite_version`; Python 3.14 is fine.
- **`shelve` numbers on Windows** look nothing like on Linux. Ask for the order of magnitude, not decimals.
- **Expect writes to lose badly and reads to tie.** In the measured run: `shelve` set ≈ 10 s, `sqlite` set ≈ 0.04 s, but reads are both ≈ 0.1 s. The argument for a key-value store is **simplicity**, not lookup speed — make them say that.
- **Server bench without a clock.** 25 minutes, then stop. It is a contrast, not a Postgres course.
- **The record becomes an essay.** One page, one row per workload, evidence in the cells. If it is longer, it will not be defended.

## Read up on

- SQLite JSON1 and expression indexes: [sqlite.org/json1.html](https://sqlite.org/json1.html) · [sqlite.org/expridx.html](https://sqlite.org/expridx.html)
- ACID vs BASE vs CAP, at the level of "what breaks when the network does": any chapter of Kleppmann's *Designing Data-Intensive Applications*.
- `pgweb` (single binary, browser UI): [github.com/sosedoff/pgweb](https://github.com/sosedoff/pgweb)
- PostgreSQL defaults worth changing for a classroom: `max_connections`, `shared_buffers`, `work_mem`.

## Harvest

**Collections, not explanations.** Nudge them toward: the two different plans for the same JSON question, `shelve`'s write cost, the `CHECK (json_valid(...))` returning from Module 4, and the moment the server stopped. Swap at the break and at the end; the decision records go on the board so the room can read the disagreements.
