## What to expect

This is the session where the course's thesis is tested against reality. Students have spent six
sessions hearing that an embedded database is enough; now they use a real server together, watch it
fail, and have to decide where the boundary is. **The goal is not to make them prefer SQLite — it is
to make the choice explicit and evidenced.**

The decision record is the only artefact that matters. Everything else feeds a row into it. The
server is shared by the whole room on purpose: every pod connects at once, concurrency is visible,
and the failure is collective. The TA helps with credentials and the first line of support; the TA
does **not** grade.

## If you are shaky on ACID, BASE, and CAP

You do not need the theory to run the task, but students will ask. Keep three pictures:

- **ACID — one database, one transaction.** *Atomicity*: all or nothing. *Consistency*: constraints
  hold before and after. *Isolation*: concurrent transactions do not see each other’s half-work.
  *Durability*: after commit, a crash does not lose it. Picture a bank transfer: the money leaves
  one account and arrives in the other, or neither happens.
- **BASE — a distributed system choosing availability.** *Basically available*, *soft state*,
  *eventually consistent*. Picture a social feed: a like may show late, then catch up. It is a
  deliberate trade, not a broken database.
- **CAP — the choice when the network splits.** A distributed system can keep *consistency* or
  *availability* when a partition happens, not both. Since partitions happen, real systems choose
  **CP** (refuse/stall rather than answer wrong) or **AP** (answer, possibly stale). An embedded
  SQLite file does not distribute, so CAP is not the choice it faces; it gives you ACID on one
  machine.

**One sentence to remember:** *ACID is a bank transfer, BASE is a social feed, CAP is the choice
when the network breaks — and SQLite is ACID on one machine because it does not distribute.*

## If a student asks about XML databases

The native XML database wave (MarkLogic, BaseX, eXist-db, Sedna) is the direct ancestor of today’s
document stores and JSON columns. It made the same promise: store documents as they arrive, let the
schema evolve, query the structure with XPath/XQuery. It was real for document-centric publishing,
archives, and catalogues; the overreach was treating XML as the universal data model for every web
API and enterprise integration, which produced SOAP/WS-* and what critics called the “angle bracket
tax.”

The balanced take: the *document/semi-structured idea* was right and survived; the *universal-XML
middleware* was a costly hype cycle. Do not let the room turn it into a pure “XML was a scam” rant;
use it to make the schema point: **the format is not the schema**. XSD, JSON Schema, `json_valid`,
and an expression index are ways to make the implicit schema explicit. Point interested students at
the [reading list](../modules/Z-resources-bank.md#xml-databases-and-the-schema-debate).

## Task 1 — JSON (25 min)

- The script creates `device` with **1,000 rows**. The 3-row version still picked the expression
  index on SQLite 3.54, but that is a planner accident; the larger table makes the lesson stable.
- Output is trimmed to five rows. Students should compare the two `EXPLAIN QUERY PLAN` lines, not
  read 1,000 rows.
- Expected: `json_extract(meta, '$.vendor')` → `SEARCH device USING INDEX ix_device_vendor`;
  `meta ->> 'vendor'` → `SCAN device`.
- The Module 4 callback is deliberate: `CHECK (json_valid(meta))` is the constraint idea returning.
  Say it once; do not re-lecture Module 4.
- Common wrong answer: “the index does not work.” The index works for the expression it was built
  on; `->>` is a different expression.

## Task 2 — Key-value (homework)

- `shelve` is platform-dependent; Windows can be much slower. Ask for **orders of magnitude**, not
  decimals across operating systems.
- Reference from the original 50k run: `shelve` set ≈ 10 s, SQLite set ≈ 0.04 s; reads both
  ≈ 0.1 s. With the 20k script the times scale roughly; the order of magnitude is the point.
- The lesson: reads tie, writes lose, and the argument for the key-value store is **simplicity**,
  not lookup speed.
- The decision record’s session-state row can use the student’s numbers or the reference. Say which
  one they used.

## Task 3 — Shared server (25 min, hands-on)

**Setup for this run (primary).** The Optiplex (8 GB) runs PostgreSQL 17 + pgweb; a Cloudflare
named tunnel exposes **pgweb only** at `hsbi-dbs.ulno.net`. Postgres stays on localhost/LAN and is
never published. One database and one role per pod (20 each); passwords on the LMS. The TA owns the
credential sheet and the first line of support. Test from a student device before the session.

**Plan B.** The instructor laptop runs the same compose file with Podman and pgweb on the
classroom LAN, or `postgres-tunnel.sh up --quick` if the LAN is not usable. The lesson is identical;
the fallback is slower to hand out credentials, not different in content.

- pgweb is the only exposed service; Postgres binds to localhost or the LAN, never a published
  5432. Cloudflare provides TLS; keep basic auth on pgweb.
- One database and one role per pod; no superuser, no `CREATEDB`, no cross-pod access.
- Test from a student device before the session. The TA owns the credential sheet and the first
  line of support.
- The existing [`postgres-tunnel.sh`](./postgres-tunnel.sh) is the named-tunnel path:
  `up hsbi-dbs.ulno.net` (one-time browser login), or `up --quick` for a temporary URL. `status`
  and `down` are the rest.

**Run the moment:**

1. Pods connect through pgweb. The TA circulates; the instructor watches the room, not the screen.
2. Create the `machine` table from Module 4; insert three rows; run one known query.
3. Two tabs or two podmates update the same row. Ask what the database did.
4. Name the moving parts of a connection: host, port, user, password, database.
5. **Stop the server** (or stop the container). Every client fails; restart. Ask what an embedded
   database would have done.
6. Students write three observations: easier, harder, one failure mode an embedded database does
   not have.

**Fallback if the server is unavailable.** Run the SQLite two-writer comparison:

```python
import sqlite3

a = sqlite3.connect("two.db", timeout=1)
b = sqlite3.connect("two.db", timeout=1)
a.execute("CREATE TABLE IF NOT EXISTS t(id INTEGER PRIMARY KEY, v INTEGER)")
a.execute("INSERT OR IGNORE INTO t VALUES (1, 0)")
a.commit()
a.execute("BEGIN IMMEDIATE")
a.execute("UPDATE t SET v = v + 1 WHERE id = 1")
try:
    b.execute("BEGIN IMMEDIATE")
    b.execute("UPDATE t SET v = v + 1 WHERE id = 1")
    b.commit()
except sqlite3.OperationalError as e:
    print("second writer:", e)
a.rollback()
```

The second writer gets `database is locked`. That is the local version of the concurrency lesson;
the three observations still apply.

## Task 4 — Decision record and defence

- Four rows: ingest, report, vendor metadata, session state; optional fifth for concurrent network
  users. The first row in the module is a filled example; use it to calibrate depth.
- Every row needs evidence from 6a/6b. “It depends” is not a row; “stale by one day, rebuilt nightly”
  is.
- Rename the last column to **“What breaks if stale/missing?”** so it applies to every row.
- Peer defence: 12 min each way, then write what changed. All pairs defend simultaneously; the
  instructor walks and listens. Ask one pair to read a changed row aloud at the end.
- The exit ticket is the “only one engine” line. If a pod cannot answer it, the record is not done.

## Where it goes wrong

- **“NoSQL means no schema.”** The JSON column has `json_valid` and an expression index on the paths
  they query — it *is* a schema. Say it.
- **The expression index that is not used.** `json_extract(meta,'$.vendor')` and
  `meta ->> 'vendor'` are different expressions. The second gets a `SCAN`. That is the task.
- **`STRICT` fails on an old SQLite.** Check `sqlite3.sqlite_version`; Python 3.14 is fine.
- **`shelve` numbers on Windows** look nothing like on Linux. Ask for the order of magnitude.
- **Expect writes to lose badly and reads to tie.** The argument for a key-value store is
  simplicity, not lookup speed — make them say that.
- **Server setup without a clock.** 25 minutes, then stop. It is a contrast, not a Postgres course.
  The TA handles credentials; the instructor handles the stop/restart.
- **The record becomes an essay.** One page, one row per workload, evidence in the cells. If it is
  longer, it will not be defended.

## Read up on

- SQLite JSON1 and expression indexes: [sqlite.org/json1.html](https://sqlite.org/json1.html) · [sqlite.org/expridx.html](https://sqlite.org/expridx.html)
- ACID vs BASE vs CAP, at the level of "what breaks when the network does": any chapter of
  Kleppmann's *Designing Data-Intensive Applications*.
- `pgweb` (single binary, browser UI): [github.com/sosedoff/pgweb](https://github.com/sosedoff/pgweb)
- PostgreSQL defaults worth changing for a classroom: `max_connections`, `shared_buffers`,
  `work_mem`.
