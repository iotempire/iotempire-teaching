## What to expect

This module replaces the old "Standard SQL / relational algebra / query optimization" lecture, and it is the one where students feel the most competent the fastest — because they are not asked to *recall* syntax, they are asked to *check* someone else's.

Three things to be ready for:

1. **The plan safari creates almost no signal.** On a four-row table everything is a `SCAN`. That is the point: say out loud that a scan is cheap until the table is large, and that the payoff comes on `warehouse.db` (240,000 rows) in Task 1.
2. **An index can make the query slower.** On this dataset, adding `ix_orderline_order` changes the dashboard plan to an index-driven join that is measurably **slower** than the scan. Do not let students "fix" their measurement to match the expected story — that negative result is the best lesson in the module.
3. **LLM output varies by model and by day.** Two pods will get different SQL for the same prompt. That is a feature: compare them.

## Before class

- [ ] Open the [SQLite EQP reference](https://www.sqlite.org/eqp.html) in a tab; you will be asked what `COVERING` means.
- [ ] Run the module's Setup once and keep the `warehouse.db` from the smoke test handy — if a student's build is short on rows, you can hand them yours.
- [ ] Decide your LLM policy for the room: which models are allowed, and whether students may use their own subscription. (The module's tasks never require a *specific* model, and Task 1 has a fallback prompt if none is available.)
- [ ] Know the difference between `.timer` (`real`/`user`/`sys`, in-process) and `time sqlite3 …` (whole process, ~1 ms floor) — the [resource bank](../modules/Z-resources-bank.md#measuring-query-time) has the three-line version.

## Opening (5 minutes)

Start from the story's failure, not from algebra: a report that was wrong for a month, and an apostrophe that took the page down. One sentence: *"Both of these shipped because nobody profiled or parameterized the generated SQL."* Then send them into the pod study. Do **not** pre-explain relational algebra — the study has the mapping table and the LLM prompt for it.

## Running the studio

- **Pod study (20 + 10).** Insist on **prediction before execution**. A pod that runs first and writes the prediction afterwards has learned nothing; ask them to show you the prediction.
- **Task A, step 2.** The index on `technician` turns equality into `SEARCH … USING INDEX`; leave the `LIKE '%ei%'` and the function-wrapped variant as `SCAN`. If a pod gets three `SEARCH`es, they indexed the wrong thing.
- **Task 1 (dashboard).** Expect `SCAN ol` plus two temp B-trees. Ask why the `customer` and `product` lookups are already fast: integer primary keys.
- **Task 2 (benchmark).** Enforce **one index at a time**, median of three runs, and both observations per step: did the plan change, did the time change. If someone re-runs the lab, `DROP INDEX IF EXISTS` first.
- **Task 3 (injection).** Run it live from the repo root, then from inside the folder — the path robustness is deliberate. The discussion question ("why is escaping by hand not a fix?") is worth five minutes of whole-room time.
- **Task 4 (algebra).** Short. If the room is behind, this is the piece to move to homework.

## Where it goes wrong

- **Trust in the LLM.** Students paste the model's SQL, it runs, and they stop. Ask: *"is the year filter in the WHERE or in a HAVING?"*, *"is that count distinct?"* — the module's prompt is designed so a plausible answer is subtly wrong.
- **`.timer` confusion.** It is a dot-command, it does not exist in Datasette or Python, and in a one-shot invocation it prints one line at the end.
- **`CREATE INDEX` errors on a second run.** "index already exists" is not a failed experiment; the module has the reset block.
- **Benchmark theatre.** If a table shows a 40× speedup on a 12-row table, the table is measuring the wrong thing.
