## What to expect

This module replaces the old "Standard SQL / relational algebra / query optimization" lecture, and it is the one where students feel the most competent the fastest — because they are not asked to *recall* syntax, they are asked to *check* someone else's.

Three things to be ready for:

1. **The plan safari creates almost no signal.** On a four-row table everything is a `SCAN`. That is the point: say out loud that a scan is cheap until the table is large, and that the payoff comes on `warehouse.db` (240,000 rows) in Task 1.
2. **An index can make the query slower.** On this dataset, adding `ix_orderline_order` changes the dashboard plan to an index-driven join that is measurably **slower** than the scan. Do not let students "fix" their measurement to match the expected story — that negative result is the best lesson in the module.
3. **LLM output varies by model and by day.** Two pods will get different SQL for the same prompt. That is a feature: compare them.

## Opening (5 minutes)

Start from the story's failure, not from algebra: a report that was wrong for a month, and an apostrophe that took the page down. One sentence: *"Both of these shipped because nobody profiled or parameterized the generated SQL."* Then send them into the pod study. Do **not** pre-explain relational algebra — the study has the mapping table and the LLM prompt for it.

## Running the studio

- **Pod study (30 + 15).** They split the material into four workstreams and must **interrupt each other** every six minutes; the clock is printed in the module (Task A at minute 20, B at 26, share at 30). Two failure modes to police: a pod that reads silently for 30 minutes and then has nothing to share, and a pod that runs queries *before* writing its predictions — ask to see the prediction.
- **Task A, step 2.** The index on `technician` turns equality into `SEARCH … USING INDEX`; leave the `LIKE '%ei%'` and the function-wrapped variant as `SCAN`. If a pod gets three `SEARCH`es, they indexed the wrong thing.
- **Task 1 (dashboard).** Expect `SCAN ol` plus two temp B-trees. Ask why the `customer` and `product` lookups are already fast: integer primary keys.
- **Task 2 (benchmark).** Enforce **one index at a time**, median of three runs, and both observations per step: did the plan change, did the time change. If someone re-runs the lab, `DROP INDEX IF EXISTS` first.
- **Task 3 (injection).** Run it live from the repo root, then from inside the folder — the path robustness is deliberate. The discussion question ("why is escaping by hand not a fix?") is worth five minutes of whole-room time.
- **Task 4 (algebra).** Short. If the room is behind, this is the piece to move to homework.

## Narrating the dashboard plan (verbatim)

This is the plan students meet in Task 1. Rehearse saying it out loud before class — the Practice row above refers to exactly this.

Before any index:

| Plan line | What it means | Say it like this |
|---|---|---|
| `SCAN ol` | reads every `order_line` row | "It starts by reading all 240,000 order lines." |
| `SEARCH o USING INTEGER PRIMARY KEY (rowid=?)` | one seek per line | "For each line it jumps straight to its order — no scan." |
| `SEARCH c USING INTEGER PRIMARY KEY (rowid=?)` | fetch the customer | "For each order it looks up the customer, to get the city." |
| `SEARCH p USING INTEGER PRIMARY KEY (rowid=?)` | fetch the product | "…and the product, to get the price." |
| `USE TEMP B-TREE FOR GROUP BY` | build groups | "Now it builds a temp structure to group by city." |
| `USE TEMP B-TREE FOR count(DISTINCT)` | deduplicate customers | "A second one, to count distinct customers per city." |
| `USE TEMP B-TREE FOR ORDER BY` | final sort | "A third: revenue isn't indexed, so sorting is another pass." |

Read it as a **loop nest**: the top line is the outer loop; every line below runs once per row above it. The `|--` glyphs are list formatting, not extra nesting — students will otherwise read them as "deeper work".

**Then the index experiment — and the point is honesty, not a speedup:**

- `ix_orders_ordered_on` **alone changes nothing**: the plan still starts `SCAN ol`. The planner prefers scanning `order_line` to driving the join from a date range.
- Add `ix_orderline_order` as well and it flips: `SEARCH o USING INDEX ix_orders_ordered_on`, then `SEARCH ol USING INDEX ix_orderline_order`, then the same three temp B-trees.
- `ix_orderline_product` is never used by this query — `product` is reached through its primary key.

So the sentence to model is "**this index changed nothing on its own, and here is why**", not "the index helped".

## COVERING INDEX — the full answer

**Definition.** A covering index contains every column the query needs (SQLite indexes always carry the rowid as well), so the engine answers from the index alone and never opens the table. The plan writes `USING COVERING INDEX` instead of `USING INDEX` precisely to record that the table was skipped.

**Show it in thirty seconds.** These outputs are real (SQLite 3.54):

```sql
CREATE TABLE t(a INTEGER, b TEXT);
CREATE INDEX i ON t(a);

EXPLAIN QUERY PLAN SELECT a    FROM t WHERE a = 1;   -- SEARCH t USING COVERING INDEX i (a=?)
EXPLAIN QUERY PLAN SELECT a, b FROM t WHERE a = 1;   -- SEARCH t USING INDEX i (a=?)
EXPLAIN QUERY PLAN SELECT COUNT(*) FROM t;           -- SCAN t USING COVERING INDEX i
```

Ask for `b` and the index no longer covers the query.

**Why it is faster.** An ordinary index search costs **two** B-tree descents per matching row: index → rowid → table row. A covering search costs **one** and skips the table entirely. On a query matching 100,000 rows, that is 100,000 table seeks you never pay.

**Four clarifications that stop the usual confusions:**

1. **Covering is about columns, not rows.** It does not mean "covers all rows" or "covers every query". The same index covers one query and fails to cover the next — which is exactly what the one-column change in the demo shows.
2. **It is orthogonal to `SCAN` vs `SEARCH`.** `SEARCH … USING COVERING INDEX` is a narrowed lookup; `SCAN … USING COVERING INDEX` is a full walk of the index (the `COUNT(*)` case). Both are covering; only one is selective.
3. **It is not free.** Every index costs storage and write work, and the planner chooses a covering path only when its cost model prefers it.
4. **`USING INDEX` is not "worse".** It means one extra hop, not a mistake.

**The one-sentence answer for students:** *"The index covered everything the query asked for, so the table was never opened."* Then add the cost sentence, because Module 5 measures it.

**If they ask "when do I design for it?"** — for a hot query that reads few columns and filters on an indexed one. `CREATE INDEX i ON t(a, b)` makes `SELECT b FROM t WHERE a = …` covering; adding a column nobody selects only costs writes.

## Where it goes wrong

- **Trust in the LLM.** Students paste the model's SQL, it runs, and they stop. Ask: *"is the year filter in the WHERE or in a HAVING?"*, *"is that count distinct?"* — the module's prompt is designed so a plausible answer is subtly wrong.
- **`.timer` confusion.** It is a dot-command, it does not exist in Datasette or Python, and in a one-shot invocation it prints one line at the end.
- **`CREATE INDEX` errors on a second run.** "index already exists" is not a failed experiment; the module has the reset block.
- **Benchmark theatre.** If a table shows a 40× speedup on a 12-row table, the table is measuring the wrong thing.
